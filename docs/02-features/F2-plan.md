# F2 — Site and building questionnaire (Q1–Q17): feature plan

Owner: Tech Lead. Shared decisions: `architecture.md` (A-n).

## Stories covered
F2-S1 Answer the saved questions, F2-S2 Define rooms, F2-S3 Catch conflicts before generating. Round 4 (client decisions CD-1, CD-2, 2026-11-20): F2-S4 Correct an edge's class, and the 3:1 rule for clamped footprints (3.1, F2-S3 wording), both in F2-T3. Also implements product sections 3.1–3.3 (site, level and roof rules) and R5 (classification, per-level signature, confirmation).

## Technical approach
- **Logic first, UI second.** All rules (edge classes, buildable mask, footprint with the CTO fallback, parking/pool fit, vegetation budget, level list, needed/available, blocking and warning lists, signatures and the R5 gate) are pure functions (A-6, A-7) landed and unit-tested in T1, including the mandatory 6.2 test. T2 and T3 are then thin controllers over `PC.site.analyse(state)` and `PC.validate(state)`.
- Every control writes through the store: appearance-class answers with `commit`, layout-class answers with `propose` on the control's commit event (A-7). Controllers re-render from state, so a cancelled proposal shows the old value again without special code.
- The site preview (Q5/Q6) draws in frame L with the street at the bottom, using the shared `View2D`; the setback zone is drawn exactly with the canvas stroke technique of A-6.
- `PC.validate(state)` returns `{ blocking: [{ code, q, level, text }], warnings: [...], summary: { plotArea, buildableArea, footprintArea, footprintPct, vegArea, vegPct, levels: [{ id, needed, available }] } }`. Stage 2 is valid when `blocking` is empty. Message texts live in one table in `validate.js`.

## Tasks (in order)

### F2-T1 — Site model, validation, signatures and R5 gate (pure logic) — **FS**
- **Scope.** `PC.site` (edge classes at 40 degrees, buildable mask, `rectFits`, footprint algorithm steps 1–7 with fallback, parking (incl. the side-yard last candidate) and pool placement, vegetation budget, memo), `PC.levels` (plan levels from Q7, `stairsExist` per 3.2, derived room names, needed = rooms + stair 10 + lift 3), `PC.validate` (all F2-S3 blocking and warning conditions, including usable-roof/pitched normalisation helper for Q9), `PC.sig` and the real `PC.store.propose` gate with an injectable confirm handler (A-7). `PC.sample` now passes validation with no warnings. `PC.debug.site()`.
- **Files.** `src/js/core/site.js`, `levels.js`, `validate.js`, `signature.js`, `store.js` (gate), `sample.js`; `tests/unit/site.test.mjs`, `footprint.test.mjs`, `validate.test.mjs`, `signature.test.mjs`.
- **Acceptance criteria.** F2-S3 (logic of every blocking and warning condition; conditions clear when the answer is fixed because the result is recomputed from state). Sections 3.1 (incl. the CTO fallback and the "does not fit this plot" conflict), 3.2. R5 classification and per-level rule. 6.2 verification numbers.
- **Dependencies.** F1-T3 (geometry, frames).
- **QA should test.** Unit (node): the exact A-6 sample assertions (584, 96.94, edge classes, bbox 2–18 / 3–28, footprint `{5.25, 8, 9.5, 15}`, 142.5, 24.4 %, not clamped, 120 of 142.5 on both levels, no warnings, parking and pool placed, vegetation 146 m2 not reduced). Footprint: rounding alone gives no clamp; a narrow plot gives `clamped`; L- and U-shaped plots hit the fallback (`moved`), with an independent check that all four corners and 20 random interior points satisfy the buildable definition; no-fit plot blocks; rotated plot (street edge not axis-aligned) gives the same footprint size as its axis-aligned twin. Each blocking code individually (empty floor, empty basement, buildable under 20, footprint % + vegetation % over 100, needed over available with both numbers in the text, out-of-range numbers). Each warning (clamped, vegetation reduced, parking omitted, pool omitted). Parking: default 1 car on a 20 x 20 m plot with a 5.25 m front yard is placed in the side yard rather than omitted. Signatures (A-7: footprint `[w, d]` + resolved street edge): unchanged for every appearance question; changed for all levels when the footprint size or the street edge changes (Q3 change, Q6 change, a plot or setback change that alters `w` or `d`), on Q14 and on stairs appearing; **a setback change that only moves the footprint (same `w`, `d`) leaves every signature identical, resets nothing and asks nothing** (same for a vertex move with that effect); changed only for the touched level on Q11–Q13; gate asks once per visit, Cancel leaves the state identical (deep equal), no question when no planned level is affected. Timing: `analyse` on a 12-vertex 100 x 100 m concave plot under 500 ms in node.
