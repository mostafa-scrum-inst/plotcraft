- **Suites:** the same runs as F4 (unit and three green; QA release gate 450.4 s / 398.8 s, 0 failures).
- **The real-r128 random-operation probe described in F4.md** covers F5 too: 48 fly-tos, 44 tour operations (start, seek, pause, resume, stop), 81 room selects, interleaved with rebuilds and context losses. Result:
  - 0 failures;
  - the highlight adds at most one mesh and one geometry, and it is disposed on reselect, rebuild and close (geometries end at 14–15);
  - no frame is requested once the flight or tour has ended or is paused.

**Findings**
1. **Design:** one animation driver serves both the finder and the tour. `end(reason)` fires exactly once, input cancels before its own delta, and a paused animation requests no frames. This is the right shape, and the probe found no stuck or double-ended animation.
2. **F5-T3a met my conditions a–c** (`F4-cto-gate.md`):
   - **a.** No phone-based tuning was done; the F5-T3b held list carries all of it.
   - **b.** The gates held.
   - **c.** It was not used as device evidence.
   - The lens shift is the cleaner choice over moving poses: the pivot, clamps and tour plan are unchanged, and only the projection centre moves.
3. **Run time:** the longest-first scheduling (F5-T3c) recovered about 20 s. Accepted.
4. **Debt (none blocks):**
   - the TL list: an API pause not shown in the UI, rotation during a tour, S6, store-only states, lint length warnings (FS, as in F4);
   - **QA:** run the `QA_FULL=1` set once more on the final release commit if anything changes after aaaddae.
