### Findings

**1. Bug: a corner drag can turn a closed plot clockwise (owner FS, fix now).**
`PC.plot.canMove` checks bounds and self-contact only. Moving one corner can produce a simple polygon with the opposite orientation, and the grid snap lets the pointer jump over the degenerate position in between. Reproduced in node: triangle (0,10), (10,10), (5,20), apex moved to (5,0): `canMove` returns `{ ok: true }`, the area becomes -50. For a 10 x 10 m square, 100 single-corner target positions on a 21 x 21 grid are accepted and give a non-positive area. Consequences:
- `PC.plot.valid` (used by `PC.draft.validState`) requires a counter-clockwise closed plot, so the autosaved draft is rejected on the next load and silently discarded. The user loses the project.
- Frame L (A-5) assumes the interior is on the left of the street edge. With a clockwise plot the whole plot lies at negative v, so the site model, footprint and everything F2–F4 build on it would be wrong.
The existing unit test only covers the flat (collinear) triangle. Fix: when the plot is closed, `canMove` also refuses a result whose signed area is not positive (same "cannot be moved across the outline" message); unit cases for the triangle and the square; one e2e case that drags an apex across the base and reloads. This is small, and it must land before the F2 site model is reviewed.

**2. Architecture and hard constraints: followed.**
One file from `build.mjs` with the single three.js tag (the build and the lint both fail otherwise); classic scripts on one global; `localStorage` only in `ui/storage.js`, every access guarded, adapter degrades to a no-op; no native dialogs, forms, network calls or downloads; Pointer Events with capture; pixel ratio capped at 2 in `View2D.resize`; canvas redraw on change only. The 28 lint rules scan both `src/` and the built file. Largest JS file is 245 lines.

**3. Layering and code quality: good.**
Core is genuinely pure: the unit loader runs core and data files in a bare `vm` context with no `window`, timers or console, so a violation fails by itself, and the lint's `core-purity` rule repeats the check. `store.js` (91 lines) is small and predictable: clone, mutate, compare, freeze, notify. Autosave being a ui-layer subscriber is the right call. `draft.js` validates strictly, which is correct given the "state only ever holds valid values" rule now in A-4. Controllers render from state and keep only transient gesture state.
One weakness: `stages.js` reaches later modules through existence checks (`PC.validate && …`, `PC.sig && …`, `PC.units && …`). Until those modules exist this is a reasonable staging device, but it fails open: a missing or misnamed module makes a stage silently valid. Remove the guards as each module lands (debt item 2).

**4. `View2D` / `draw2d` and the store gate as a base for F2–F5: sound.**
- `View2D` knows nothing about plots: world box, draw callback, `hitTest` returning an opaque handle, tap and drag callbacks. The site preview and plan editor can pass frame-L or frame-P coordinates as "world" unchanged, and y-up matches "street at the bottom". The gesture machine handles the cases that usually go wrong on phones (second finger cancels a drag, nothing taps until all pointers are up, lost capture, stale pointers), and the Tech Lead proved the lost-pointer tests by mutation.
- For F3-T2: a drag that starts on a handle is a drag, anything else pans. In a plan where rooms fill the footprint, one-finger panning is therefore not available on a room; that matches F3-S2 (two fingers pan and zoom), so no change is needed, but the plan-editor plan should say so.
- `draw2d.edgeLabels` and the label collision helpers are generic and reusable for room labels.
- The store's `propose` is a pass-through today with the right shape (promise of boolean, callers already use it for layout-class changes: vertex release, close, reopen). F2-T1 can put the gate inside without touching callers.
- Per commit the store does one deep clone, two `JSON.stringify` and a deep freeze. Fine at this state size and because drags are transient; watch it only if F3-T2 commits during a drag.

**5. Tests: they test real behaviour.**
E2E drives the built page by screen coordinates obtained from `PC.debug.toScreen`, with real touch sequences through CDP, and fails on any page error, console error, native dialog or unexpected request. QA's suites are independent of the developer's and found real defects (clipped summary sheet, truncated readouts, missing border labels). The unit tests caught both of my mutations. The gap is finding 1: the invariant "a committed closed plot is counter-clockwise" was asserted for closing and for drafts, never for corner moves. For F2 onward: when the architecture states an invariant, one test must attack it through every operation that can change the data.

**6. Test runtime.**
About 7 minutes, sequential, almost all of it browser time (measured: unit under 1 s, `shell.spec` 45 s, QA F1-T1 layout 79 s). With four more features at this rate a full run would pass 25 minutes and people will stop running it. The machine has 2 cores. Two cheap measures (debt item 3): run the e2e and QA files two at a time, and define the focused run for the inner loop (build, lint, unit, the task's own spec files), keeping the full run mandatory at the Tech Lead's implementation review and at QA sign-off. If the full run still exceeds about 15 minutes by F4, QA trims overlap between `tests/e2e` and `tests/qa` rather than anyone skipping the run.

**7. `architecture.md` drift: still coherent, with small stale spots.**
The amendments (autosave in ui, valid-values-only state, `streetEdge` stored on close, numeric id order, contract files, tap limit, fit control, split `site-*.js` files) are consistent with each other and with the code. Stale: the A-2 table still puts `PC.stages` in `store.js` and lists a `PC.debug` shape that no longer matches (`view`, `plotLabels` exist; `frames` does not); A-5 writes `l2t(house, …)` while the code takes the centre; the A-4 code comment says `streetEdge: null = default rule` while the bullet below says null only before closing; A-5 says orientation is normalised "once, when the shape is closed" without stating that corner moves must preserve it (finding 1). One tidy-up pass is enough (debt item 4).
